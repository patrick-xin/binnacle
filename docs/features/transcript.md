# Transcript

Rows `binnacle-transcript`, `binnacle-transcript-view` · Code `binnacle:packages/binnacle/src/plugins/transcript/index.ts#apply`, `binnacle:packages/binnacle/src/plugins/transcript-view/index.ts#apply` · Intent: [Authoring](../../intents/authoring/intent.md)

## What a person can do

- Read the transcript, with the row `binnacle-transcript-view` on, as binnacle ships it:
  - a prompt as `› ` and its text, in the `accent` Tone, each line it wraps to under its text, or `› ` alone with no text;
  - an answer's reasoning in the `dim` Tone, then its text as markdown, wrapped at the width: headings, bold, italic, inline code, code blocks, lists, quotes, links and rules, a list item's and a quote's lines that wrap under its text. An answer with neither draws nothing;
  - a tool call as one line, `⏺ <tool>(<its arguments>)`, and its result as one line, `⎿ ` and its first line of text, or `✗ ` and its first line in the `error` Tone when it failed, each cut at the width. With no text, `⎿ (no text)` or `✗ failed`;
  - context the person did not type as one dim line that names its producer, such as `· context: agent-instructions`;
  - a command, a retry, a compaction and how a turn ended as one line each, such as `/compact`, `retrying (1/3): <why>` in the `warning` Tone, `· context compacted`, `· interrupted`, and `✗ <why>` in the `error` Tone when a turn failed;
  - nothing for every other event, which takes no row, and the Mark passes over it;
  - a blank line after a prompt, an answer and a tool result, but not after a context, a call or a notice, so a call and its result stand together.
- Watch the answer stream through the same pieces: its reasoning, its text as markdown, an unclosed code block as code to the end, a blank line, then each tool call with the arguments so far. The committed answer and its calls draw the same rows.
- Read a stored session the same way.
- Turn the row `binnacle-transcript-view` off, and read the session's events raw: each event's seq and type, then its data as JSON, and the answer that streams as one live block, each content block's deltas glued.
- Scroll the transcript with the wheel.
- Give the transcript the Focus: the newest event is Marked, in inverse video. Up and down move the Mark one event, and stop at the ends.
- Fold the Marked event with enter. With the view, an event of more than one line draws its first line, then `… <n> more lines` in the `muted` Tone. A prompt, and an event of one line, do not fold: a click on them only Marks them. Raw, it folds to its header line, which ends with how many of its lines it hides: `▸ #<seq> <type> (<n> lines)`. A click on an event's first line folds or unfolds it, and Marks it. A click on another of its lines Marks it, and folds nothing, unless a Look marked that line.
- Keep the folds and the Mark as events come and the live block streams. The Mark is not drawn while the transcript has no Focus, and the same event is Marked when it comes back.

## What an author can change

- Read the transcript's state: the model `transcript`, `binnacle.modelOf('transcript')`, of the type `TranscriptState` from `binnacle/plugins/transcript`. It holds `events`, `live`, `folded` and `marked`.
- Fold an event, or a part of it, or Mark it: set `folded`, an array of regions as strings, or `marked`, a seq. An event's own region is its seq, `'12'`, and a part of it a region such as `'12/body'`. Such as each tool result folded when it comes, from a watcher of the model.
- The keys that move the Mark and fold: `binnacle.bind('transcript.up', …)`, `transcript.down` and `transcript.fold`, such as `j` and `k` to move the Mark.
- What a key or a click does: set `transcript.up`, `transcript.down`, `transcript.fold` or `transcript.click` by its id, and run `beneath()` to keep the default. Every fold, by a key or a click, goes through `transcript.fold`, so `binnacle.action('transcript.fold', { run: () => {} })` stops every fold.
- What a click on a line does: a transcript Look returns each line as a `Line` from `binnacle/plugins/transcript`, a string or `{ text, fold: '<region>' }` or `{ text, run: '<action>' }`. A click on a `fold` line folds its region, and on a `run` line runs its action, given the cell clicked. Such as a `[-]` at the end of a call's first line that folds its body, `'<seq>/body'`, and not the whole line.
- Where on a line a click acts: `{ text, fold, from }` or `{ text, run, from }` acts only at the column `from` of its text and after it, counted in cells without its styles, such as a call's first line `⏺ ls · 0.1s [-]` whose `from` is where its `[-]` starts, so a click on `[-]` folds and a click on the title only Marks.
- How one type of event is drawn: the Look `transcript.event.<type>`, such as `transcript.event.tool/call`, or every event's with `transcript.event`, beneath them. Given the event and `{ folded, isFolded, width }`, `folded` whether the event's own region is folded and `isFolded(region)` whether any region is, it returns the event's lines, such as a tool call as one line cut at the width. An event whose Look draws no line takes no row.
- Change one piece of the view with its Look, given plain data and `{ width, time }`, never dsh's shapes, `time` the event's in epoch milliseconds, or `undefined` in the answer that streams: `transcript.prompt` and `transcript.answer` and `transcript.reasoning` are given a text (`TextLook`), `transcript.call` `{ name, args }` (`CallLook`), `transcript.result` `{ text, failed }` (`ResultLook`), `transcript.context` `{ producer }` (`ContextLook`), and `transcript.notice` `{ kind, text, severity }` (`NoticeLook`), the types from `binnacle/plugins/transcript-view`. Such as the prompts wrapped with `> ` before each line, with `wrap` from `binnacle`, each prompt after the time it was sent, the reasoning hidden, committed and streaming, with `transcript.reasoning` alone, or the answers indented, with `markdown` from `binnacle`. The default answer draws with `markdown`, so a markdown Look, such as `markdown.code`, changes one kind of block of every answer ([Kit](kit.md)). A Look that draws nothing takes the piece out, and an event left with no line takes no row, its blank line included.
- Read an event without knowing dsh's shapes, with the readers from `binnacle/plugins/transcript`: `textOf(event)`, the text of a person's message, an answer's or a tool result's; `reasoningOf(event)`, an answer's reasoning; `callOf(event)`, a tool call's `{ name, args }`; `producerOf(event)`, the producer of context the person did not type; `noticeOf(event)`, what a command, a retry, a compaction or a turn's end says; `isPrompt(event)`, whether it is a prompt the person typed; `failed(event)`, whether it is a tool result that failed; and `withoutReasoning(event)`, the event with its reasoning taken out. Such as a Look that draws each prompt as `> <text>`, or hides an answer's reasoning with `beneath(withoutReasoning(event), at)`.
- How the answer that streams is drawn: the Look `transcript.live`, given its blocks and the width, such as with its reasoning left out of the raw transcript. With the view on, the view sets it, and its pieces' Looks change it.
- Replace the transcript: turn off its row, and place a Part of their own in the `transcript` Place.

## How it is built

- **The view is a row of its own**, as the Requests have a model's row and a view's row. `binnacle-transcript-view` lays its Looks over `binnacle-transcript`'s raw ones: on `transcript.event.<type>` for each type it draws, on `transcript.event` beneath them to draw nothing, and on `transcript.live`. The transcript keeps its raw Looks as its default, so a person who turns the view off sees what dsh logged, and an author can start from it. The view uses only what an author can import: the readers, `toPlainText`, `truncateToWidth`, `wrap` and `markdown`.
- **A piece is a Look, an event's type is not**: a piece is what an author asks to change, such as "the prompts" or "the reasoning". One type holds more than one piece: a `user/message` is a prompt or a context, and an `assistant/message` holds the reasoning and the answer. The view's Look of a type reads the event with the readers, and draws its pieces through `binnacle.lookOf`. Each piece is given the text as it came, Untrusted Text, and its default makes it plain, a text's own line breaks kept.
- **A piece's `at` is `{ width, time }`**, `time` the event's, as plain data as the pieces are, so a prompt drawn with the time it was sent is a Look of `transcript.prompt` alone, not of its type. A piece of the answer that streams is given no `time`, as it is no event yet.
- **The folds and the blank lines are the type's Look**, not the pieces'. It joins its pieces' lines. With none, the event draws no line, and takes no row. Folded, with more than one line, it draws the first and `… <n> more lines`, `n` counted before the core wraps them. A prompt does not fold, and neither does an event of one line: the type's Look draws its first line as `{ text }`, a Line that folds nothing, so a click on it only Marks. Then it adds the blank line after a prompt, an answer and a result, which the count leaves out.
- **The pieces' defaults:** a prompt is `wrap`ped with the `mark` glyph and a space before it, in `accent`. An answer's text is drawn with `markdown`, which makes it plain, and its reasoning is wrapped in `dim`. A call, a result, a context and a notice are cut at the width with the `more` glyph, a call's arguments and a notice's text on one line, their newlines made spaces. A result shows its first line that is not blank. A notice draws `info` as `· <text>` in `muted`, `warning` in `warning`, and `error` as `✗ <text>` in `error`, and a command's `info` notice as it is, so `/compact` reads as the person typed it.
- **The notices** are read from the event that says how a thing ended, so nothing says it twice: `command/run` and `command/done` with a text, `llm/retry`, `compaction/end`, and a `turn/end` that failed, was aborted or stopped at the output limit. dsh appends a compaction's summary before the compaction can still fail, so `compaction/summary` gives none.
- **The answer that streams** draws its blocks as three pieces, whatever their order in the stream: the reasoning blocks joined, the text blocks joined, the blank line when either drew a line, then each tool call. That is the committed answer's order, as dsh commits the answer, then its calls' events. Between the answer's commit and its calls' events, the calls do not draw.
- **Wide content wraps**, as in pi: the core wraps each line at the width.
- **The Mark is the Part's cursor**, on the Marked event's header line, so the core keeps it in view.
- **The model `transcript`** is `{ events, live, folded, marked }`. The transcript keeps its own events and live blocks, and sets them on the model at each event and each frame, so an author who sets `events` or `live` has them replaced then. `folded` and `marked` are only the model's: the actions, the Focus and an author change them, and the view draws them. An array is what a Model's `set` changes in place, as `folded.push('12')`.
- **The live blocks end when the answer commits**: the transcript sets `live` to `undefined` when the Chat's `assistant/message` or `assistant/attempt` commits, as well as at the stream's end, since dsh commits the event before it ends the stream. So the answer never draws twice.
- **The live blocks** are in the answer's order, each a `kind`, `text`, `reasoning` or `tool-call`, its `text`, and a tool call's `name` once dsh gives it, as dsh's deltas carry it. The view makes the name plain when it draws it.
- **A Look for each event, by its type, then `transcript.event`**, as an instance's Look lies on its kind's. Its type is `EventLook`, and the live block's is `LiveLook`, each returning `Line[]`. The default draws the header, then the JSON, then a blank line, or the header with its count while folded. The JSON of an event's data is made once, when the event comes.
- **Each Look is called at each draw**, as a Part's lines are, so the lines follow the theme, the Looks and their models. Each frame of a streaming answer calls every committed event's Look, and parses the streaming answer's markdown again: a cost the prototype accepts. If a long session is slow, the fix is a cache that the core tells of each change.
- **The view Marks and folds**, not the Look: the Mark is the inverse video of an event's first line, set again after each style sequence in it, so a reset in any form does not end it, and the Look is told whether its event is folded.
- **Where the Mark is drawn:** on the Marked event if it draws a line, else the next event that draws, else the one before, else nowhere. The same holds for a `marked` that is no event. Drawing never changes `marked`, so the Mark comes back to its event when it draws again. Up and down move from where the Mark is drawn, among the events that draw, and set `marked` to the event they reach. Enter folds the event where the Mark is drawn, which a person sees Marked.
- **A click lands on what was drawn:** on the line it was drawn on, in the lines drawn last. The transcript draws a line's `text` alone, and keeps the event that drew each line and what each marked line does, by its index before the core wraps it.
- **Every fold is `transcript.fold`**, so one empty action takes out every fold. Given no cell, at a key, it folds the event where the Mark is drawn: its first region marked `fold` on a line it draws, else its own region. Given a cell, it folds the region of the line there when the line is marked `fold`, the event's own region when the line is the event's first and a plain string, and nothing else. `transcript.click` Marks the event of the line clicked, then runs the line's `run` action, else `transcript.fold`, with `binnacle.run(id, at)`, so an author's action by either id takes the click. A line with both `fold` and `run` runs its action. A marked line acts only from its `from`, a column of its text that is 0 by default: a click before it is as on a plain line that is not its event's first, so it Marks and folds nothing, even on the event's first line. Enter folds the first `fold` region whatever its `from`. The live block's lines can be marked too, but a click on them Marks no event.
- **Regions are strings**: an event's own region is its seq as a string, and a Look names the rest, such as `'<seq>/body'`. The raw default and the view's Looks read `folded`, the event's own region, and draw the first line of an event that folds as a plain string, so a click on it folds the event as before. An event that draws no line keeps its regions folded, as a `marked` that draws nothing is kept.
- **The keys are actions** of the Place `transcript`: `transcript.up`, `transcript.down` and `transcript.fold` take the Gesture Table's `tui.select.up`, `tui.select.down` and `tui.select.confirm` keys by default, and `transcript.click` takes `click`. The Part takes no key, so a key that would type does nothing, and esc still interrupts. Up and down at the ends, and each action while no event is Marked, do nothing.
- **The readers of an event** read its data as unknown, so each is safe on any type and any shape. `textOf` reads `user/message`, `assistant/message` and `tool/result`, and joins their `text` blocks with nothing between, as dsh does. `reasoningOf` joins an `assistant/message`'s `reasoning` blocks the same way. `callOf` is a `tool/call` whose `name` is a string, with its `arguments` string or `''`. `producerOf` is the `source.kind` of a `user/message` that is not a prompt, or `'unknown'`. `isPrompt` is a `user/message` whose `source.kind` is `user`: dsh gives each producer of context its own kind. `failed` is a `tool/result` whose message has `isError`, or that has an `error`. `withoutReasoning` takes the `reasoning` blocks out of an `assistant/message`'s message, and out of the stream of an `assistant/message` or an `assistant/attempt`: the `reasoning-chunks` records, and each `chunk` record of a reasoning delta, or of the start or the end of a reasoning block. It makes a new event, and gives an event with no reasoning as it is, so the default Look keeps the JSON it made when the event came.
- **The live block is not an event**: it cannot be Marked or folded.
