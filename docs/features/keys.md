# Keys

A person reaches what content offers from the keyboard, on either screen. On the main screen no pointer reaches binnacle, so there a key is the only way. Every key named here is a binding in one table, and a person can give any of them a different key — or give an offer beyond the first a key of its own.

- **Step in.** From the composer, Shift+Tab focuses the nearest thing on screen that offers something: a fold cut short, or one opened.
- **Move.** While something has focus, Tab or ↓ moves focus to the next such thing and Shift+Tab or ↑ to the previous, in screen order, wrapping.
- **Open.** Enter does what the focused thing offers first: it opens a cut fold, or folds an open one again.
- **Any offer, not only the first.** A key can be bound to one kind of offer — copy, open, answer — and does that on the focused thing, wherever the thing offers it. Where it offers no such thing, the key does nothing and focus stays; with nothing focused, the key reaches the composer as typing.
- **Rebind.** Ask for a different key for anything bound — quitting, switching screens, the Trajectory, submitting a line, moving the cursor — and it answers everywhere that key is read: the composer, the alternate screen, and binnacle's own keys. The key a binding leaves reaches the composer as typing.
- **Step out.** Esc gives the keyboard back to the composer. So does any key Keys does not answer, and that key reaches the composer as typed, so typing is never lost.
- **Interrupt.** While nothing has focus, Esc stops a running turn, keeping what waits in the agent's inbox; while nothing runs, the key reaches the composer as typing. While something has focus, Esc steps out instead.
- **Answer.** While a decision or a question sits in the composer's place, the keyboard is its offers': Tab and the arrows move among them, and Enter does what the first offers — allow once, or an option of the question asked. A key bound to an offer's kind invokes it wherever the seat offers it, whichever offer has focus: once a person binds `dismiss`, that key rejects an approval or cancels a question — until then, Tab reaches reject or cancel and Enter invokes it ([Approvals](approvals.md), [Questions](questions.md)). Allowing, refusing and cancelling are never a click — `grant` and `dismiss` are keys pressed on purpose — while a question's options answer the pointer too. Answering gives the composer back as it was, with what was typed.
- **A plugin's screen.** A placed screen opens on the key its plugin offers — or the key a person rebound it to — in the transcript's place; from the main screen, opening switches to the fullscreen. The same key, or Esc, returns to the transcript as it was — its scroll, focus and folds — and, where opening switched, to the screen the person was on. While it is open, the screen answers the keys the transcript would, on itself: Shift+Tab steps in, and with something on it focused, Tab, ↓, ↑ and Enter move focus and open, with UI state of the screen's own. The fullscreen's own keys scroll, search and select it, the composer below stays live, and nothing moves on the transcript beneath; Ctrl+C and Ctrl+T still answer, and leaving the fullscreen closes it.
- **See focus.** A row in the accent tone says what Enter will do, in the focused thing's own words (`▸ show 12 more lines`, `▸ fold to 3 lines`). A cut fold's `… 12 more lines` row becomes that row, and a fold that is one line becomes it with its title kept on — `▸ ∴ thinking · show 12 more lines` — open or closed: the fold's own row replaced in its place, wrapping to more rows at a narrow width as any line does. An open fold that shows rows draws the row anew beneath what it holds. On the fullscreen, focus brings what it is on into view.
- **On the main screen**, focus that reaches an entry already printed switches to the fullscreen, with that entry in view and focused. Enter opens it in place there, and Ctrl+T back finds the main screen as it was. Focus on something not yet printed stays on the main screen, drawn there. Focus the main screen cannot draw, on an entry printed before a switch to it or as printing catches up, is set aside rather than a printed row changed, and the keyboard goes back to the composer. Ctrl+T back to the fullscreen gives it back, drawn and in view, unless a key was pressed in between: then it is forgotten, so Enter sends what was typed.
- Ctrl+C quits and Ctrl+T switches screens: the defaults, as rebindable as any binding.

## How it works

One key table (`binnacle:packages/binnacle/src/ui/keys.ts#KEYBINDINGS`), held with pi-tui's own bindings in one manager and installed with pi-tui's `setKeybindings`, so the composer and the alternate screen read the same table. It answers a press only, once: a key held or let go, which a kitty-protocol terminal also reports, is answered by nothing binnacle binds ([ADR 13](../adr/0013-a-key-means-something-only-through-the-one-key-table.md)). A key the table resolves becomes a `key` gesture, and the gesture table gives it its meaning ([ADR 1](../adr/0001-content-offers-affordances-the-surface-owns-gestures.md)); what is bound to the host — quitting, switching screens, interrupting a running turn — the host answers ([ADR 11](../adr/0011-placements-reach-the-whole-screen-and-the-built-in-surface-is-placed-through-them.md)). The key a plugin offers for a screen it placed is a binding in the same table, named for the screen (`binnacle.screen.<name>`); the manager is rebuilt with the offers as they come and go, carrying what a person rebound, so one table still answers every key. Whether something has focus decides which bindings are live, and that is decided in the table: with nothing focused, the composer keeps every key but Shift+Tab, Ctrl+C, Ctrl+T and Esc — Esc resolves to `binnacle.interrupt`, which the host answers while a turn runs, and while nothing runs the key reaches the composer as typing. Where more than one live binding answers a key, the one the person bound resolves, over one that only defaults to it — the defaults keep their order otherwise, and two ids a disposal leaves on one key keep it too. Keys arrive ahead of the composer, through pi-tui's input listener. Lines in the composer's slot that offer something take the keyboard while they stand, ahead of what is being read, their first offer focused as they take it — what they ask is the person's to answer next — and answering gives the keyboard back to the composer; lines elsewhere take no focus ([Authoring](authoring.md)). Focus is UI state (`binnacle:packages/binnacle/src/ui/state.ts#UiState`) held by the pane that answers for the screen being read — the transcript pane for the transcript, or the screen pane for a placed screen that is open — each answering key gestures on the screen it last drew and reporting what to bring into view, or a printed entry asking for the fullscreen (`binnacle:packages/binnacle/src/panes/transcript.ts#TranscriptPane`, `binnacle:packages/binnacle/src/panes/screen.ts#ScreenPane`).

What a person binds arrives through the same door as everything an author registers: `ctx.binnacle.keys(bindings)` (`binnacle:packages/binnacle/src/api.ts#Registrations`), each binding id to the key or keys it answers to, as pi-tui names them — and what was handed over cannot be changed by changing the object after. An id is pi-tui's own (`tui.input.submit`), binnacle's (`binnacle.quit`), a placed screen's (`binnacle.screen.<name>`, whether or not the screen is placed yet) or an affordance kind's (`binnacle.copy`), which no key holds until one is bound. Registrations layer by id, the newest over the older; disposing one gives its ids back to what bound them before — the default, where nothing did. What the registrations leave is the table's user bindings, held in pi-tui's own manager (`pi:packages/tui/src/keybindings.ts#KeybindingsManager`), never a table of binnacle's, and a registration coming or going rebinds the table and installs it again wherever keys are read. A registration that is no record of binding ids, names an id no binding has, binds a key that is no string, or brings two ids to one key is refused where it is registered, saying what to change; the last pi-tui reports as a conflict among a person's bindings, and binnacle refuses it rather than resolve it silently (`binnacle:packages/binnacle/src/ui/keys.ts#refusedBindings`). An affordance's key resolves only while something has focus, to a `key` gesture of its kind.

## Choices

- The default keys, each named with what it does in `--help`, a person's to change:

| Binding | Keys |
| --- | --- |
| step in, or previous | `shift+tab`; also `up` while focused |
| next, while focused | `tab`, `down` |
| primary, while focused | `enter` |
| step out, while focused | `escape` |
| quit | `ctrl+c` |
| switch screens | `ctrl+t` |
| interrupt the running turn, while nothing has focus | `escape` |
| each kind of offer, copy and open among them | unbound |

- Focus is drawn as a row in the accent tone, saying what Enter will do in the thing's own words: in place of the fold's own marker row or line — which can wrap to more at a narrow width, as any line does — or, on an open fold that shows rows, added beneath what it holds.
- Step in lands on the nearest thing that offers something — the last on screen, by the composer.
- Focus set aside by the main screen comes back with the fullscreen only if nothing was pressed in between, so a line typed there is never answered by focus.
- On the main screen, focus reaching a printed entry switches to the fullscreen rather than reprint the scrollback ([ADR 12](../adr/0012-on-the-main-screen-a-printed-row-never-changes.md)); bringing what is focused into view scrolls only when it is out of view.
- The key a plugin offers for a screen it placed is the plugin's to choose, a binding in the same table and so rebindable as any other, whether or not the screen is placed yet.
- `--help` names binnacle's bindings and each affordance's, with each key and what it does, `(unbound)` where none is bound — and nothing a profile's plugins offer or rebind, for dsh parses the command line as the row applies, before any plugin has registered (`dsh:packages/boot/cmdline/src/index.ts#parseCmdline`).
- Whether a string names a key is pi-tui's to say, and it exports nothing that says it: only a key that is no string is refused, and a string that names no key is bound and never answers.
- A disposal cannot be refused, so it can leave two ids on one key — when the registration disposed was what kept them apart. The key then does whichever the table resolves first; binding one of them elsewhere sets it right.
- A person's bindings live in a plugin of their own, written by hand or by an author they ask ([ADR 0](../adr/0000-everything-is-a-plugin-a-person-changes-by-asking-an-author-agent.md)); binnacle reads no file of them.
