Boxes in binnacle

A field guide to every box binnacle draws: what it's for, where it goes, how a person interacts with it, and what an author agent can change. Everything here was read from the code and records on main. The last section lists where the code, the records and the words have drifted apart.

read at main 5abb6c5 (sections 1–11 at 1454184; layout and theme unchanged since) · 2026-10-02 · mockups drawn in dusk (legacy's dark palette, the worked example #97 ports; binnacle's own theme follows the terminal's sixteen colours)

1 · Words first: container, dialog, card

binnacle's records already rule on these three words, and two of them don't mean what they mean elsewhere. ADR 11 rejected naming a container by how it's drawn ("a card, a border"), because nothing would then tell a decision apart from a tool's output. So the vocabulary is:

You might saybinnacle's wordWhat it isKind
containershow and askThe closed set of containers (ADR 11), named for what the surface is doing: a show holds what it shows and did not write, an ask holds what it asks or offers.block (node)
dialogthe dialog slotA place, not a block: the slot drawn over the page, centred, on pi-tui's overlay stack. What's placed there is usually an ask.place (slot)
cardtool card (ours) · card (dsh's)card is dsh's word: the kind of view a tool presents a call as. A tool card is binnacle drawing that call inside a show. binnacle has no node called card.show, by convention
panel, box with a fillbandContent padded inside a background the theme names by meaning (userMessageBg). It's drawn for what a person sent.block (node)
Rule of thumb. A block is what a view returns (data). A place is where the host seats it (a slot, or a placed screen). An ask can stand in any place. The dialog is one place an ask can stand.

3 · show: the container for what the surface shows

Anatomy (ui/layout.ts#show):

  • title: Span[] is drawn in tone (default text) and wraps.
  • The child is laid out at width − 1 − spacing.show. Every row is prefixed with chrome.gutter in borderMuted.
  • opens: '<fold id>' makes the title the line that fold folds under. The head region then offers that fold's expand plus copy (text = everything the show holds). The fold's own rows offer nothing, so a click on output does nothing and selecting text leaves it alone.
  • When the width leaves no room, the gutter is dropped and the child is drawn full width.

Built-in uses: every tool card (the generic row, and binnacle's own card in views/entries.ts), and the presented entry (files the agent handed over).

5 · ask: the frame for what the surface asks or offers

Anatomy (ui/layout.ts#ask):

  • The border is chrome.border (rounded by default, or set by chrome.frame), drawn in edge (default border). Approvals and Questions use borderAccent.
  • title is one line on the top edge. If it doesn't fit (width − 6), it's left off whole, never cut.
  • The bottom edge names the answering keys, e.g. enter select · tab next, from the key table as the person bound them. It's drawn only when the pane is handed the key table (composer seat, dialog) and the ask holds an offer. next appears only when there are two or more offers.
  • The padding is spacing.ask columns inside each side. background fills every line, border included.
  • With no room inside, the frame is dropped and the child is drawn bare.

6 · The dialog slot

  • Draws the newest lines placement placed in 'dialog', via pi-tui showOverlay(pane, {anchor:'center', width:'80%', maxHeight:'80%', nonCapturing:true}). Disposing it gives back the one before, or the page.
  • Keyboard precedence (host/index.ts keys): a dialog that offers something comes first, then composer-seat lines that offer something, then the reading pane (the transcript, or an open placed screen). The seat's first offer is focused on taking the keyboard.
  • It stands over whichever screen the person switches to. On quit it's removed, so the printed session is left without it.
  • No built-in feature uses it. It's tested only through author plugins in test/host/index.test.ts. The Approvals and Questions pages both say "a dialog over the page waits until a feature needs one". #82 (open on a card) is the open candidate.

7 · band and fold, briefly

band is pi-tui's Box with spacing.band padding and a theme.backgrounds[name] fill. binnacle draws one for what a person sent (prompt, userMessageBg). It offers nothing and takes no keys. It holds a child, but it isn't one of ADR 11's containers (see drift D2).

› add a dusk theme file

fold is the only box that changes shape by gesture. It shows rows (node, then the theme's per-kind folds, then 3) and offers expand. With rows: 0 it rides its title line: ∴ thinking · 5 lines. Opened, the label becomes fold to N lines / fold it away. Toggling is UI state (ui/state.ts#act) and never reaches a plugin's invoke.

Content declares affordances. One gesture table gives every gesture its meaning (ADR 7), and one key table names every key (ADR 8). No box handles input itself.

The gesture table (ui/gestures.ts#meaning)

  • click invokes the primary (first) affordance of the innermost region under the pointer that offers something, if that kind allows the pointer.
  • wheel scrolls the innermost region that overflows. drag selects text. hover does nothing.
  • keys: focus.next / focus.previous cycle (wrapping) through focusable regions. focus.out unfocuses. primary (Enter) invokes the focused region's first affordance. A key bound to an affordance kind (binnacle.copy …, unbound by default) invokes that kind on the first region under focus that offers it.
  • focus is drawn by the box: a focused offer gets an extra row ▸ label beneath its content. A focused cut fold's marker becomes ▸ show N more lines in place, so focusing doesn't move the layout.

11 · Styling a tool card, as the author agent

A person says "try a few styles for the tool cards". This section covers what an author agent can actually hand them today, and where it hits a wall.

The two levers, and the split between them

lever A · no code · hot

a theme file

<profile>/themes/<name>.json, chosen by the binnacle-theme row's config (theme / light / dark). Saving it redraws the screen with no restart, and a broken file shows a notice naming its path while the last theme stays. It's checked against theme.schema.json. It changes how every card looks: tones, marks, gutter and frame glyphs, spacing, fold starts and fold words. It applies to every card at once. Rows already printed to the main screen's scrollback keep their old look (ADR 14).

lever B · a plugin

a card row (and an output view)

ctx.binnacle.card(kind, row) changes what a card is made of, per card kind: which spans the head holds, what goes under the gutter, how output is folded. It names tones and marks, never colours. ctx.binnacle.view('output', …) restyles the output fold on every card, built-in and author rows alike.

The split. The row says what is drawn and which named tone. The theme says what that tone looks like. To get a new look on one part of a card, add a tone in the theme ("tones": {"toolPill": {…}}) and name it in the row. The theme must be registered first, because a row naming a tone the theme doesn't give is refused (and see D1 for where that refusal lands).

Can and can't, read from the code

AreaCanCan't (and why)
Shape Any head spans: text, tones, marks, live {since} / {until} timers. Any child: text, markdown, stack, folds (fold(child, rows) per call), a band, a nested show. Decline per call, so the next row draws it. A different row per card kind. Return anything but a show at the top, so the head-over-gutter shape is fixed (views/cards.ts#Shown). Drop the gutter for one card: frame:none blanks it for every show, and the column stays. Put an ask in a card (it parses, but ADR 11 says a card shows and doesn't ask).
Colour Recolour any tone, and add new ones: colour, background, bold, dim, italic, underline. Exact hex, okhsl/oklch, 256-index or the sixteen. vars. Light and dark variants that follow the terminal. Name a colour in a row: only tone names, and an unknown one is refused. Escape codes in text are drawn as text (ADR 12). Give one card its own gutter tone: borderMuted is hard-wired in layout.ts#show and shared with the composer's frame (D8).
Glyphs Marks (running, done, failed, or new ones), gutter, frame set, focus ▸, cut …, separator ·. Fold words (cut, show, to …) with {n} and {lines}. A gutter or border glyph wider than one column (refused). An animated spinner: only {since} ticks, once a second. Card-only marks: done and failed are the transcript's too.
Room spacing.show (gutter to content), spacing.indent (sub-calls), spacing.gap (between entries), folds.tool and folds.result rows and open. Know the width: a row is a function of its parts, so there's no right-aligned "took 1.4s", no width-filling rule, and no proportional bar. Side-by-side columns: no horizontal node, so no split diff. A per-tool fold start in the theme, which is keyed by entry kind (tool), not tool name. The row can pass rows to fold() instead. A full-line fill on a single line: a tone's background covers the text only.
Data The presented title, the card kind, returned (the presenter's object), resultText, reason, took, made (sub-calls), waiting. The tool's name or raw arguments: CardParts carries neither, and ADR 15 forbids reading arguments by name. A row is drawn once and kept (ADR 10), so anything it reads besides its parts needs invalidate('tool').
Input The head opens and folds output (opens) and offers copy of everything the card holds. Folds of its own, toggled by click and Enter. Offer an action that does something: in the transcript only expand and copy act (panes/transcript.ts), and views have no invoke, so a "re-run" or open offer is inert. copy on an author offer copies nothing: only a show's head gets the region text. A person says "make it feel like dusk, but make the asks louder and the cards calmer". This section covers what a theme reaches on each box, what a node chooses for itself, what nobody can change, and what happens when boxes are nested.

D · Ask inside a transcript entry: "pick one to rerun".

A view can return an ask, and the transcript's seat gives keys, so the bottom edge promises enter select. But views have no invoke, and in the transcript only expand and copy act. Enter does nothing.

Gaps this surfaces

These are added to section 14 as D12–D16.

  • Three untoned pieces of chrome (ask title, ask hints, cut marker) break "a view names a tone, never a colour" from the other side. The surface paints them in no tone, so no theme reaches them.
  • No focus tone: focus borrows accent.
  • Frame is surface-wide: ADR 11 says ask and show exist so that "restyling one doesn't restyle both", yet chrome.frame restyles both.
  • Asks in views advertise keys that do nothing.
  • The closed words, chrome and spacing mean an author's box can't be themed through the same parts binnacle's are, which strains ADR 0's "same registrations".

14 · Deviations to watch

Each one is a place where code, records and words disagree. Severity is about how far it pulls the project off its own commitments, not how hard it is to fix.

high · verifiedD1. A malformed card row skips every row beneath it

plugins/tool-cards/cards.ts#drawCard checks only drawn.kind === 'show'. A row that returns {kind:'show', title: 5} passes, and the result fails parseNode later in the view stack. Probed: with rows [good, bad], drawCard returns the bad show, and parseNode then throws "a show's title is 5". The good row is never tried. The entry falls to binnacle's own card, blamed on binnacle.view(tool), not binnacle.card(generic).

This contradicts the card JSDoc in api.ts ("returns no show … is drawn over by the row beneath, saying why"), and the root AGENTS.md rule that author code is parsed where it enters.

parseNode each row's return inside drawCard, and treat a failure as a refusal by that row.

medD2. band sits outside ADR 11's closed set of containers

ADR 11 says a block that holds another names what the surface is doing, and that "these containers are a closed set" (ask, show). It rejected naming a container by how it's drawn. band holds a child and is named by its fill. The glossary lists it with no word on its standing. Either ADR 11 should say a band is a fill, not a container, or band is a third container that needs a meaning-based name ("what the person wrote").

Settle it in ADR 11 (amend in place while young) before #85's blocks page restates it.

medD3. "Every decision has an ask as its parent" isn't held by anything

ADR 11 commits that every decision and every tool call has the surface's container as its parent. Tool calls are held: a card row must return a show. Decisions are not. parseNode accepts an offer with grant/dismiss anywhere, and a composer-seat placement of bare offers takes the keyboard with no frame and no key hints. Only the pointer policy protects it.

Decide whether this is a gate (refuse grant/dismiss outside an ask at parse) or a convention (then soften ADR 11's wording).

medD4. Asks are called "card" in the code and tests

Approvals' and Questions' node builders are both named card(). Approvals' comment says "Card takes keyboard as newest composer placement", and host tests assert "the card offers both" and "a click on the card does nothing". The glossary reserves card for dsh's tool-view kind and says binnacle has no node of that name, and ADR 11 rejected the word for a container. This is exactly the blur that keeps "dialog/card/container" from meaning one thing.

Rename them to ask(), and "the ask" in comments and test titles.

medD5. The dialog is a door with no built-in feature behind it

The glossary describes the dialog as holding "an ask, as a rule", and ADR 13 lists "a dialog over the page" among the places. Yet both built-in asks chose the composer seat, and nothing built-in places there. #32 ("every door, each proven by the built-in feature placed behind it") is the record that says this matters. Proof is author tests only. #85 will give the dialog a room, so the first built-in user is near.

Name its first built-in user (#82 open, or a /settings picker) on #32.

med · knownD6. A tall ask is cut off: bottom edge lost, focus on invisible offers

This is tracked as #85 (bug). Its prerequisite #105 has merged. Until it lands, "the bottom edge names the keys that answer it" doesn't hold for long asks in either place.

lowD7. A focused offer repeats its label beneath itself

layout.ts appends a focus row ▸ label under a focused offer's content. In an approval, the child text equals the label, so a seated approval reads allow once / ▸ allow once / reject (the asserted behaviour in test/ui/layout.test.ts:642). Questions do the same for each option. It may be intended (the focus row says what Enter does), but inside an ask it reads as a duplicate.

Consider marking the focused line in place within an ask, as a focused fold marker already does.

lowD8. ask and show are asymmetric in what a node may name

An ask names its edge tone and background per node. A show names only its title tone, and its gutter is hard-wired to borderMuted in layout.ts#show. That fits "restyle by meaning", but a card row can't mark one show as different (a failing call's gutter in error, say) without a new theme name.

lowD9. Approvals has no test folder of its own

The root AGENTS.md says tests mirror src/<path>. test/plugins/ has composer, questions, status-line, tool-cards and trajectory, but no approvals/. Its behaviour is asserted in test/host/index.test.ts (it's applied on the agent's scope by the host). That's defensible, but undocumented in the plugins folder note.

lowD10. Small record and code drift

ADR 11's status says "its colours are revised by ADR 16, if that is accepted", and ADR 16 and 17 are still proposed. In ui/theme.ts#marks, the comment for retry ("a model request dsh tries again after it failed") is appended to the workflow line, and retry has none. The chrome.border JSDoc says "the border an ask is framed in", while chrome.frame also sets the show's gutter (documented on the Theme page, not on the field).

lowD11. A card row can't tell which tool it's drawing

CardParts holds the presented title and card kind, but not the call's name. The tool cards plugin has it (entry.call.name) and passes it only into the output part. A row styling "bash differently from read" has to guess from the title, though the output view gets part.tool. This shapes what a person can ask for at the grain ADR 0 promises, so decide whether it's a deliberate omission (ADR 15) or a gap.

Either hand the row tool as the output part does, or say in the CardParts JSDoc why it's withheld.

medD12. Three pieces of box chrome are drawn in no tone

In ui/layout.ts: an ask's title and its bottom-edge key hints are written between edge-toned pieces with no tone of their own, and an unfocused fold's cut marker (… N more lines) has none either. No theme can reach them, so a person asking to "dim the more-lines marker" or "colour the ask title" can't be served at any grain, which falls short of ADR 0.

Give each a tone (pi has muted / dim, or new names), and let an ask's title be spans like a show's.

medD13. chrome.frame restyles ask and show together

ADR 11 rejected one container drawn by its border because "restyling one restyled both". frame sets the ask border and the show gutter at once, and no node can pick its frame. Pieces can be set apart, so it's escapable, but the headline knob contradicts the record, and per-instance frames (a heavy approval) are impossible.

Split into frame.ask / frame.show, or let an ask name a frame as it names an edge tone.

medD14. An ask drawn by a view advertises keys that do nothing

The transcript is seated with keys (host/seats.ts), so an ask a view returns gets enter select · tab next on its bottom edge. Views have no invoke, and the transcript acts only on expand and copy. The edge's promise is false, and nothing refuses a choose / grant / answer offer in a view.

Either hints count only offers the seat can act on, or a view refuses offers it can't honour (ties to D3).

lowD15. Focus has no tone of its own

The focus row and focused fold markers paint in accent, also used by links, the prompt and steer marks, and searches. Recolouring focus recolours all of them.

A focus tone, defaulting to accent.

lowD16. An author's boxes can't be themed through the parts binnacle's are

tones, backgrounds, marks and folds accept new names. words, chrome and spacing refuse them (ui/theme-changes.ts). An author's own ask can't say its own hint words, and its own box can't take a spacing a person tunes in the theme, so authors hard-code what binnacle's own boxes keep themeable.
